# Bug Record (Reversa Bugs)

> Generated by Reversa on {{DATE}}. This file is the contract of this project's bug record.
> Source of truth: each `<context>/bugs/<ID>/bug.md`. Everything in `generated/` is regenerable projection.

## Project configuration

```yaml
closure_policy: {{CLOSURE_POLICY}}   # local-software | package | production-service
control_mode: gated                  # supervised | gated | autonomous
```

- `closure_policy` defines what "resolved" requires:
  - `local-software`: regression tests passing + spec verdict
  - `package`: previous + merge + corrected version published (+ required backports)
  - `production-service`: previous + delivery + observation window with no recurrence
- `control_mode: gated` (default): reading, isolated reproduction, and diagnosis flow without approval;
  mandatory gate for applying tests, applying change set, changing the effective spec, using an external
  harness with access to the project, and any destructive operation.

## Structure

Bugs are grouped by **context** (feature, module, or use case, in the language of the reporter). Each context is an aggregator folder with EVERYTHING for that area: bugs, inspections, and views. The folder is born on demand, when the first problem in the area is reported; nothing is created empty.

```text
_reversa_bugs/
├── README.md                    this contract
├── taxonomy.yaml                controlled vocabulary of area/module/feature
└── <context>/                   e.g. sistema-de-credito/, carrinho-de-compras/
    ├── bugs/BUG-<date>-<suffix>-<slug>/   single bug folder (IMMUTABLE address, never moves)
    │   ├── bug.md               canonical record
    │   ├── evidence/  ├── debate/  └── fix/
    ├── inspections/<sweep>/     context deep-sweep reports
    └── generated/               context views, regenerated by /reversa-debugger-graph
```

## Lifecycle

`status`: `open` → `active` → `resolved`. `phase` details the stage inside `active`
(mitigating, reproducing, diagnosing, testing, patching, delivering, observing, awaiting-human).
Blocking is a condition (`blocking:`), never a status. Every closure has a `resolution_kind`.

**Completion lock:** when the closure policy is satisfied, the bug receives `DONE.md` in its folder and
becomes READ-ONLY for all agents. Reopening: remove the lock consciously, or register a new bug
with `regression-of`. The list of locked bugs appears in the context's `graph.html` (derived view,
without manual editing).

## Traceability rule

Every bug MUST identify:

1. The spec section that defines the expected behavior (effective spec = original + in-force addenda).
   Without a spec, the bug carries the `spec-gap` label and the gap is treated before resolution.
2. The affected code (where it appears) and, after investigation, the root cause (where it was born),
   with epistemic state and evidence.
3. The reproduction and regression tests.

A bug CANNOT be `resolved: fixed` with `traceability.specs`, `root_cause` (confirmed) or
`regression_tests` empty.

## Agent protocol

1. Registering (`/reversa-debugger`) NEVER fixes. Fixing (`/reversa-debugger-fix`) follows two approval
   gates with diff (tests that fail; change set that makes the tests pass).
2. The original spec is NEVER edited. A spec change becomes a versioned and immutable addendum in
   `<output_folder>/addenda/bug-<ID>-vNNN.md`, with the human decision recorded.
3. The code diff and the spec diff/addendum are recorded TOGETHER in the bug's Resolution.
4. Bugs with `visibility: restricted` stay out of the views and nothing exploitable goes to an external harness.
5. Relationships and root cause have epistemic state: a hypothesis is not a fact.

## Conventions

- Canonical ID: `BUG-<YYYYMMDD>-<suffix>` (merge-safe). `display_number` is the human nickname.
- References are always by ID; views resolve the path.
- Evidence in `evidence/`, never huge logs inside the Markdown.
- Full schema: see `bug-schema` in the Reversa documentation (agents/reversa-debugger/references/).
